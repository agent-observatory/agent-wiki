# Agent Wiki 아키텍처

**사용자의 작업과 기록의 수집·정제를 분리한다.** Claude·Codex는 사용자와 작업하고 필요할 때 Wiki를 조회한다. 별도 Collector가 클라이언트 기록을 읽어 원격에 보관하고, 별도 백그라운드 실행이 군집화·정제한다.

읽기 전용 Collector → 불변 원문 → 원격 Worker → 근거가 있는 지식 개정으로 이어진다. 배포·실제 모델 검증 상태는 [운영 현황](../OPERATIONS.md), 연결과 API는 [수집·정제 계약](agent-memory.md)을 따른다.

## 전체 구성

![사용자 작업·별도 Collector·백그라운드 정제와 원격 Wiki](../assets/wiki-deployment.svg)

작업 에이전트와 Collector를 별도 프로세스로 둔다. 세션 안에 수집 명령·정제 요청을 넣거나 턴 종료 훅에서 업로드를 기다리게 하지 않는다. Collector·정제 장애는 사용자 작업과 독립적으로 처리한다. 필요한 지식 조회에는 통신 시간이 들지만, 그 조회가 새 수집·정제 완료를 기다리지는 않는다.

## 세션 식별과 직접 업로드

**세션은 `Workspace + 에이전트 종류 + 원본 세션 ID`로 식별한다.** 에이전트 종류는 Codex·Claude Code다. 기기 ID는 수집 출처로 분리하고, 서버의 연속 수신 위치는 기기·파일 세대별로 관리한다. 같은 세션에 메시지 101~110이 추가되면, 이미 받은 1~100을 다시 보내지 않고 확인된 위치 이후만 전송한다.

Collector → API의 위치 확인·업로드 허가 → Collector의 마스킹·zstd 압축 → Object Storage 직접 업로드 → 서버 검증·L1 등록 → 별도 L2 정제 순서다. 큰 파일 본문은 Caddy·API를 통과하지 않는다. 임시 파일 도착만으로 적재 완료 처리하지 않으며 **중복 판정·불변 원문 등록·수신 위치 확정은 서버 책임**이다.

내용 해시는 전송 묶음의 동일성, 원본 세션 ID는 대화의 동일성을 판별한다. 일부 겹치는 기록은 서버가 별도로 대조한다. 앞부분 수정·파일 축소·다른 기기 수집에서는 오프셋을 그대로 신뢰하지 않는다. [수집 계약과 1~100 → 101~110 예시](agent-memory.md#세션-식별과-증분-수집).

## 책임과 비용 경계

| 구성 | 책임 | 실행 방식 |
| --- | --- | --- |
| 작업 에이전트 | 사용자 질답·업무, 필요한 지식·근거 조회 | CLI 조회 가능 |
| Collector | 허용 기록 읽기·마스킹·증분 압축·직접 업로드 | Codex·Claude JSONL, macOS 30분 주기 |
| 백그라운드 정제 | 원격 원문·기존 지식 조회, 군집화·정정·근거 연결 | VM Worker, Workspace별 외부 AI 설정 |
| Skill | 조회 또는 별도 정제 실행의 방법론 | 지침만 제공. 프로세스·스케줄러 아님 |
| CLI | 인증·범위·자료 전송·조회·반영 | 구현. 자체 수집·모델 실행 없음 |
| Wiki API | 업로드 허가·수신 검증 조율·중복/등록 판정·근거·개정·검색 | API와 비동기 수신 검증 |
| PostgreSQL / Object Storage | 지식·개정·정제 기록·근거 / 불변 원문 보관본 | 운영 중 |

Collector 자체는 모델을 호출하지 않는다. 세션·프로젝트·시간에 따른 수집 단위와, 의미에 따른 군집화를 구분한다. 후자는 별도 정제 실행의 일이며 임베딩은 필수가 아니다.

L2는 기존 VM의 Worker가 외부 AI API로 실행한다. 개인 에이전트 CLI나 대화 플랜을 사용하지 않는다. Workspace의 **수집·AI 정제**에서 제공자·모델·키·입출력 한도·일일 호출 수·활성 여부를 설정한다. 기본은 중지, 일일 24회다. NVIDIA DeepSeek Flash를 기본으로 사용하고 Pro·Kimi K3를 선택할 수 있다. 모델 선택과 실제 응답 품질·무료 이용 자격은 구분한다. 조회에는 모델을 호출하지 않는다.

키는 서버의 암호화 키로 암호화하고 브라우저에 반환하지 않는다. 실행마다 설정·프롬프트 버전·원문·참고 지식 개정·모델 출력·보고된 토큰을 보존한다. PostgreSQL 작업 테이블로 동시성 1, 5분 임대, 최대 3번 시도와 최종 실패를 관리한다. 결과 반영과 완료 상태는 같은 트랜잭션이다. 출력 저장 뒤 중단되면 같은 반영 키로 결과를 복구한다. 일일 한도는 UTC 기준 시도 횟수이며 비용 상한이 아니다.

### 모델 선택

| 모델 | 역할 | NVIDIA 모델 ID · 추론 설정 |
| --- | --- | --- |
| **DeepSeek Flash** | 청크별 결정·사실·태그·근거 추출의 기본 | `deepseek-ai/deepseek-v4-flash-0731` · 처음에는 `none` |
| DeepSeek Pro | 더 신중한 정제가 필요할 때 수동 모델 교체 | `deepseek-ai/deepseek-v4-pro-0813` · `none` / `high` / `max` |
| Kimi K3 | 비교 평가·모델 교체 선택지 | `moonshotai/kimi-k3` · `low` / `high` / `max` |

Pro·Kimi는 설정에서 수동 교체하는 모델이다. Pro 전용 자동 재검토 경로를 두거나 모든 청크를 Flash 다음 Pro로 자동 이중 호출하지 않는다. 초기에는 Flash 하나로 처리하고, 미해결 충돌은 검토 대상으로 보존한다. 대표 자료의 결정 누락·정정·인용 정확성을 비교한 뒤 재검토 범위를 정한다. 모델의 자신감이나 도착 시각만으로 결정의 유효성을 판단하지 않는다.

2026-09-13 NVIDIA [Flash API](https://docs.api.nvidia.com/nim/re/reference/deepseek-ai-deepseek-v4-flash-0731-infer)·[Pro API](https://docs.api.nvidia.com/nim/re/reference/deepseek-ai-deepseek-v4-pro-0813-infer)·[Kimi API](https://docs.api.nvidia.com/nim/reference/moonshotai-kimi-k3-infer)를 확인했다. DeepSeek의 호출 옵션은 `none`·`high`·`max`이며 `low`를 보내지 않는다. Flash 모델 소개와 호출 명세의 표현이 달라 호출 명세와 실제 응답을 기준으로 검증한다. NVIDIA `202`는 처리 대기이므로 요청 ID로 결과를 조회한다. 모델 교체는 다음 작업부터 적용한다.

## 대용량 원문과 텍스트 정제

**압축은 전송·저장량을 줄이고, 청킹은 모델의 입력량을 제한한다.** Collector는 증분을 최대 4MiB 조각으로 나눠 zstd로 독립 압축한다. 서버 수신 검증은 AI 설정이 중지돼도 진행한다. 전송 조각은 바이트 크기·재시도를 기준으로 정하며 L2 청크와 같은 크기를 강제하지 않는다.

L2에는 **텍스트만** 보낸다. 이미지 본문·이미지 URL을 모델에 전달하거나 자동 OCR·이미지 분석을 실행하지 않는다. 이미지 본문은 마스킹 L1에 보관하고 텍스트 투영의 분석 생략 범위를 기록한다. L1은 JSON 정규화 보관본이므로 로컬 파일과 바이트 단위로 동일하지 않다. 텍스트에 나온 이미지 설명을 직접 관찰한 사실로 승격하지 않는다. 파일의 MB나 압축률로 모델 토큰을 추정하지 않는다.

```text
L1 보관본 → 세션 이벤트 파싱 → 텍스트·원문 위치 추출
→ 대화·도구 호출 관계를 고려한 청킹 → Flash로 지식 후보·근거 추출
→ 기존 지식과 비교·검증 → L3 개정 반영
```

| 단계 | 범위 |
| --- | --- |
| **1단계 · 지금** | 증분 직접 업로드·zstd·수신 검증, 텍스트 투영·기본 구조 청킹, 청크별 상태·근거 검증·키워드 검색 |
| 2단계 · 품질 개선 | 먼 청크·세션의 결정·취소·대체 관계 통합, 재검토 대상 선별·평가 |
| 3단계 · 필요할 때 | 검색 누락이 확인되면 임베딩·혼합 검색 평가. 대용량 정제의 필수 조건 아님 |

태그는 분류, 청킹은 입력 분할, 임베딩은 의미 검색을 위한 선택이다. 서로 대체하는 단계가 아니므로 기본 청킹을 초기 범위에 포함한다. 1단계에서도 근거 없는 덮어쓰기를 막고 미해결 충돌을 남긴다. 세부 청크·한도·재시도 계약은 [수집·정제 계약](agent-memory.md#정제와-재시도)을 따른다.


## L1–L5와 지식 모델

![수집·정제와 사용자 조회를 분리한 계층](../assets/wiki-layers.svg)

L1–L5는 우리 제품의 논리 모델이며 공식 표준이나 하나의 동기 요청 순서가 아니다. L2는 작업 세션과 분리된 실행, L5는 사용자의 작업 에이전트다.

| 계층 | 역할 | 변경 기준 |
| --- | --- | --- |
| L1 원문 | 서버가 검증·등록한 대화·문서·코드 보관본 | 불변. 새 기록은 새 원문으로 추가 |
| L2 정제 | 여러 원문 군집화·기존 지식 비교·주장과 근거 연결 | 방법론은 개선 가능. 과거 실행과 입력은 보존 |
| L3 Wiki | Memory·Article·Glossary와 개정·관계 | 지식은 새 개정으로 갱신 |
| L4 조회 | 키워드 검색·시작 문서·인용 자료 구성 | 지식 개정과 근거를 고정해 반환 |
| L5 활용 | 조회한 근거로 답변·작업 | 사용자 요청에 필요한 조회만 수행 |

Memory는 짧은 주장·결정, Article은 설명 문서, Glossary는 용어·별칭이다. 직렬 생성 단계가 아니다. 원문 개정 → 정제 실행 → 지식 개정·주장별 근거를 연결한다. 프로젝트 역사도 원문 자체가 아니라 원격 Wiki에서 개정하는 지식이다. [리니지 상세](agent-memory.md#원문은-불변-지식은-개정).

Schema·Index·Log·Lint는 구조 규칙·목차·실행 이력·점검을 뜻한다. LLM Wiki·OpenMetadata의 용례를 참고하며 제품 전체를 설치하거나 우리 확장을 표준으로 부르지 않는다. 구조 검증과 해석의 타당성을 구분한다.

## Workspace와 사용자 흐름

Workspace는 자료·권한·검색의 격리 단위다. Folder는 기본 위치 하나, Tag는 여러 개의 분류다. CLI 프로젝트 이름은 서버·Workspace·태그를 묶은 연결 별칭이며 별도 권한 모델이 아니다. 첫 적용은 개인 작업 Workspace, 개발 기록 Folder, `agent-observatory`·`agent-wiki` Tag다.

| 사용자 작업 | 별도 백그라운드 처리 |
| --- | --- |
| Claude·Codex로 평소처럼 질답·작업 | Collector가 클라이언트가 남긴 기록을 읽음 |
| 이전 결정이 필요하면 Wiki 조회 | 허용한 변경분을 원격 원문으로 보관 |
| 근거를 읽고 현재 작업 계속 | 기존 지식과 비교해 군집화·정제·새 개정 반영 |
| 필요하면 웹에서 지식 정정·출처 확인 | 정정·추가 원문을 이후 정제의 근거로 사용 |

왼쪽 흐름은 오른쪽 흐름의 완료를 기다리지 않는다. 매 턴·시작·종료·컴팩션에 수집·정제·조회 명령을 의무화하지 않는다. 아직 수집하지 못한 내용은 이미 기억한다고 설명하지 않는다. 원문 없는 수동 메모는 작성자 진술로 구분한다.

## 검색과 Context

PostgreSQL 제목·본문·태그·용어 별칭·명시적 문서 연결과 `pg_trgm` 인덱스로 시작한다. 임베딩·pgvector는 후속 후보이며 외부 API나 Comsat 모델은 필요할 때 평가한다. 일반 검색은 모델 호출 없이 수행한다.

에이전트가 질문의 핵심어를 골라 검색하고 필요한 원문만 추가로 읽는다. `recall`은 에이전트가 유지하는 시작 문서·목차의 조회이며 서버가 즉석 요약하지 않는다. 백그라운드 정제가 아직 끝나지 않았으면 기존에 반영된 지식을 반환한다. 최신성을 추정하지 않고 확인 시점과 개정을 함께 읽는다.

현재 Context는 지식 최대 6개·본문 발췌 8,000자·전체 JSON 16,000자로 제한한다. 문서당 주장 최대 8개·주장당 근거 최대 4개를 요약하며 잘림을 표시한다. 전체 내용은 개정·원문 상세 조회로 확인한다. 삭제·대체·미확인을 구분하며 한국어 별칭 품질은 실제 질문으로 다듬는다.

Obsidian 앱은 사용하지 않는다. 관계는 PostgreSQL로 시작한다. Cytoscape.js 시각화, Apache AGE, OpenMetadata 전체 도입, MCP, 로컬 전체 자료 복제는 미확정·후속 후보다.

## L4 · 필요한 기억을 찾아오는 조회 정책

**원격 Wiki를 매 턴 읽거나 통째로 내려받지 않는다.** 현재 대화·코드만으로 충분한지, 프로젝트의 과거 결정·근거가 필요한지를 작업 에이전트가 판단한다. 난이도보다 **과거 맥락에 대한 의존성**이 조회 기준이다. 이 절은 조회 정책의 설계이며 기존 CLI 위에 추가할 동작을 설명한다.

### 조회 판단과 사용자 제어

| 상황 | 기본 동작 |
| --- | --- |
| 현재 대화·코드에 질문을 해결할 근거가 충분함 | 원격 조회 생략 |
| 과거 결정·선호·제약·이유·미완료 작업을 묻거나 그것에 의존하는 변경 | 관련 Wiki 조회 |
| 기억하는 내용과 현재 코드·사용자 설명이 충돌함 | 과거 근거 조회 후 현재 사실과 구분 |
| 프로젝트 고유 이력이 필요 없는 일반 지식·단순 편집 | 조회 생략 |
| 사용자가 Wiki 확인을 명시적으로 요청·금지함 | 해당 요청을 우선 적용 |

기본 모드는 **자동**, 선택 모드는 **항상 조회**와 **조회 안 함**으로 둔다. ‘항상 조회’는 요청마다 관련 근거를 확인한다는 뜻이며 전체 Wiki를 가져오는 동작이 아니다. ‘조회 안 함’에서는 원격 확인을 생략했다고 구분한다. 프로젝트 기본값과 현재 작업의 선택을 분리하고, 현재 사용자의 지시가 기본값보다 우선한다. 모드 이름은 설계 용어이며 구체적인 CLI 플래그·설정 키는 구현 때 정한다.

```mermaid
flowchart TD
    request[사용자 요청] --> mode{조회 모드}
    mode -->|조회 안 함| local[현재 대화와 코드로 작업]
    mode -->|자동| need{과거 맥락이 필요한가}
    mode -->|항상 조회| lookup[관련 Wiki 검색]
    need -->|아니오| local
    need -->|예| reuse{현재 대화의 근거로 충분한가}
    reuse -->|예| use[고정 개정과 근거 활용]
    reuse -->|아니오| lookup
    lookup --> detail[필요한 지식과 원문 구간 확인]
    detail --> use
```

### 조회 스킬과 도구의 책임

| 구성 | 책임 |
| --- | --- |
| 조회 Skill | 조회·생략 조건, 검색어 작성, 근거 해석·인용 지침 |
| CLI | 인증·Workspace 범위·검색·개정·원문 조회, 응답 크기·시간 제한 |
| 클라이언트 하네스 | 설치된 지침·도구를 에이전트가 발견하도록 연결. 지원되는 범위에서 도구 사용 제어 |
| Wiki L4 API | 권한 검사·키워드 검색·근거 반환. 조회를 위해 별도 모델 호출이나 L2 완료를 요구하지 않음 |

초기는 **조회 Skill 하나 + 기존 CLI**로 시작한다. Skill은 L5 작업 에이전트의 조회 필요성 판단·근거 선택·인용을 안내하고, CLI는 실제 검색·개정·원문 조회를 수행한다. 먼저 조회 누락·과도한 호출·근거 품질을 검증한다. 조회 연결에는 읽기 전용 권한을 사용하고 수집·정제 실행 권한은 부여하지 않는다.

**플러그인은 스킬이 여러 개로 늘어나 묶음 설치·갱신이 필요할 때 도입한다.** 그때 기존 Skill과 CLI를 재사용한다. [OpenAI 공식 패키징 문서](https://developers.openai.com/plugins/build/plugins)에서 스킬과 선택적인 MCP 연결의 묶음 배포를 확인했다(2026-09-12). MCP는 CLI 실행이 어려운 클라이언트를 지원할 필요가 생기면 추가한다. 초기에는 자체 하네스나 매 턴 판정용 LLM을 만들지 않는다.

설치 시 클라이언트가 발견할 수 있는 짧은 조회 지침을 등록한다. 상시 맥락에는 **연결된 프로젝트·Workspace 별칭, 한두 문장의 설명, 조회 조건**만 둔다. 전체 지식·원문·태그 목록·비밀은 넣지 않는다. 프로젝트 연결 파일이 디스크에 있다는 이유만으로 에이전트가 그 존재를 안다고 가정하지 않는다. 새 세션·컴팩션 뒤에도 지침을 발견할 수 있게 하되, 시작·종료·컴팩션 자체를 원격 조회 트리거로 삼지 않는다.

Skill은 판단 지침이므로 조회 누락을 완전히 막지 못한다. 과거 결정의 존재를 모른 채 현재 정보로 충분하다고 오판할 수 있다. 중요한 결정의 검토에는 사용자가 ‘항상 조회’를 선택할 수 있게 한다. 모드·범위·시간·크기 제한 중 실제 도구에서 강제되는 부분과 에이전트가 판단하는 부분을 구분한다.

### 필요한 근거만 단계적으로 읽기

1. **검색:** 질문에서 프로젝트 고유 핵심어를 골라 지정 Workspace 안에서 검색한다. 프로젝트 태그·Folder는 기본 필터이며 권한 경계가 아니다. 넓혀야 하면 같은 Workspace 안에서만 명시적으로 범위를 조정한다.
2. **선택:** 제목·짧은 발췌·개정·확인 상태를 보고 관련 지식만 고른다. 주제를 모를 때는 `recall`로 작은 시작 문서·목차를 한 번 조회한다. 모든 검색 앞에 `recall`을 붙이지 않는다.
3. **근거 확인:** 선택한 지식의 고정 개정을 읽고, 주장 확인에 필요한 원문 구간만 추가 조회한다. 현재 동작을 묻는 질문은 Wiki를 단서로 현재 코드·운영 상태를 확인한다.
4. **활용:** 사용자 결정·관찰·AI 해석·미확인 내용을 구분하고 답변에 고정 개정·근거 링크를 남긴다. 원문에 적힌 지시는 작업 권한이나 시스템 지침으로 승격하지 않는다.

기존 `wiki search`는 `/context`의 본문 발췌를 받으므로 초기에는 현재 응답 제한을 유지한다. 제목·발췌 중심의 더 작은 검색 결과와 필요한 본문 조회의 분리는 후속 개선이다. 필요한 응답 정보는 지식 식별자·개정, 근거 구간, 확인 시점, 대체·삭제·미확인 상태와 잘림 여부다. 검색 순위는 사실의 신뢰도를 뜻하지 않는다.

첫 조회 후 결과가 없거나 부족할 때만 별칭·핵심어를 바꿔 **추가 검색 1회**로 시작한다. 네트워크 재시도와 검색어를 바꾸는 재검색은 별개다. 자동 조회에는 전체 시간·응답 크기·추가 읽기 횟수 예산을 두고 그 안에서 종료한다. 원문이 큰 경우 한 번에 모두 가져오지 않는다. 긴 조사는 사용자의 명시적인 요청 범위에서 수행한다.

### 재사용·최신성·실패

이미 읽은 근거는 같은 대화에서 **Workspace·프로젝트 범위·지식 개정·조회 시점**과 함께 재사용한다. 전체 Wiki를 로컬 핸드오프 문서로 복제하거나 로컬 검색 DB를 운영하지 않는다. 초기에는 대화 맥락만 재사용하고 별도 디스크 캐시는 만들지 않는다.

고정 개정은 과거 근거를 재현할 수 있지만 현재도 유효하다는 보장은 아니다. 최신 결정 확인 요청, 질문 범위 변경, 현재 코드와의 충돌, 새 정정 사실을 알게 된 경우 다시 조회한다. 과거 결정의 이유를 설명하는 데는 이미 확보한 고정 개정을 재사용할 수 있다. 다시 조회할 때는 현재 권한·삭제·대체 상태를 확인하며, 권한 철회나 삭제 사실을 알게 된 기존 자료는 재사용하지 않는다. 대화에 이미 들어온 자료를 서버가 원격으로 회수할 수 있다고 가정하지 않는다.

**검색 결과 없음·접근 불가·통신 실패·수집/정제 미반영**을 구분한다. 검색 결과가 없다는 이유로 과거 결정이 없었다고 단정하지 않는다. 원격 실패 때 현재 정보로 가능한 작업은 계속하되, 결정에 꼭 필요한 근거라면 확인 불가를 알리고 사용자에게 묻는다. L4 조회가 수집·정제를 실행하거나 그 완료를 기다리게 하지 않는다.

### 구현 순서와 확인 기준

1. 기존 조회 Skill에 판단표·사용자 모드·단계적 읽기·재사용 기준을 반영한다. CLI 설치 안내의 시작·재개 시 일괄 `recall` 문구도 이 기준에 맞춘다.
2. CLI에 조회 모드 전달·읽기 범위·호출 예산을 연결하고, 조회 Skill과 CLI의 프로젝트 연결을 설치한다. 클라이언트별 지원 여부는 실제 새 세션·컴팩션 뒤에 확인한다.
3. 작은 질문 묶음으로 **필요한 조회 누락, 불필요한 조회, 근거 일치, 호출 수·지연·반환량**을 비교한다. 내부 추론이나 대화 원문을 운영 로그에 저장하지 않는다.

| 확인할 질문·상황 | 기대 결과 |
| --- | --- |
| “왜 단일 VM으로 결정했지?” | Wiki에서 결정 당시 근거를 조회·인용 |
| “이 함수 이름을 바꿔줘” | 현재 코드로 충분하면 원격 호출 없음 |
| 같은 근거를 사용하는 후속 질문 | 대화 안의 고정 개정 재사용 |
| “그 뒤 결정이 바뀌었는지도 확인해” | 현재 개정·대체 상태 재조회 |
| 새 세션에서 과거 제약에 영향을 주는 변경 요청 | 짧은 연결 지침을 발견하고 관련 제약 조회 |
| 조회 금지·서버 장애·다른 Workspace 자료 | 지시·권한 준수, 실패와 자료 없음 구분 |

## 단일 Compute VM 배포

기존 A1 VM 1대·2 OCPU·12GB에 Caddy·Next.js·Fastify API·Worker·PostgreSQL 5개를 Compose로 관리한다. Worker는 동시성 1·CPU 최대 0.5·메모리 최대 2GB다. 추가 클라우드 자원을 만들지 않는다.

| 구성 | 역할 |
| --- | --- |
| DuckDNS | `agent-wiki.duckdns.org`를 VM 공인 주소에 연결. HTTP 요청을 중계하지 않음 |
| Caddy | HTTPS 접속·웹/API 경로 분기, 인증서 발급 기관과 통신해 자동 발급·갱신 |
| 연결 Block Volume 50GB | PostgreSQL 데이터와 Caddy 인증서·설정을 별도 경로에 보관 |
| 부트 볼륨 50GB | 운영체제·Docker 등 호스트 구성 |
| Object Storage | 원격 원문 보관본. 인증서 저장소와 구분 |
| DataGrip | 공인 5432·별도 ID/비밀번호·TLS. 사용자 선택에 따라 IP 제한·Bastion 없음 |
| 내부 연결 | Compose 서비스 이름. 웹·API 포트는 내부 전용 |

기존 메모리 상한은 Caddy 0.25GB·Web 2GB·API 2GB·DB 3GB다. DNS 갱신과 인증서 갱신은 다른 작업이며 VM 공인 주소가 바뀌면 DNS 연결을 갱신해야 한다. Caddy 재배포 때 인증서 볼륨을 유지한다.

사용자는 PAYG 업그레이드를 완료했지만 유료 사용은 허용하지 않았다. 새 자원·사양·모델 연결 전에 계정 전체 사용량·조건·비용을 확인한다. 예산은 강제 지출 상한이 아니다. 백업·복원은 후속 과제다.

## 배포와 운영

![사용자 작업과 별도 수집·정제의 운영 경로](../assets/wiki-operations.svg)

GitHub main 변경 → Actions 검증 → 외부 ARM64 이미지 빌드·GHCR 게시 → SSH를 통한 자동 배포로 이어진다. VM은 이미지를 미리 받고 변경된 앱만 교체한다. VM·DB·Caddy·볼륨은 유지하며 전체 Compose 종료는 하지 않는다.

계획 배포는 Caddy에서 외부 신규 유입을 막고 Web·내부 API 요청을 마친 뒤 API를 종료한다. Worker는 신규 수신을 멈추고 진행 결과를 최대 90초 동안 마친다. Compose 유예는 120초이며, Web → Worker → API 순으로 종료한다. API 종료 예산 30초·Compose 유예 45초다. 조회 재시도는 일시 오류에 한정하고 쓰기는 같은 멱등 키로 결과부터 확인한다. 짧은 중단은 허용한다.

앱은 OTel Logs Data Model에 맞춘 JSON을 stdout/stderr에 남긴다. Docker syslog → 호스트 rsyslog → OCI Unified Monitoring Agent → OCI Logging으로 전송한다. 호스트 수집기는 VM의 시스템 서비스이며 별도 사이드카 컨테이너가 아니다. 전체 배포도에서는 생략하고 운영도에만 표시한다.

오류는 Connector Hub → OCI Monitoring 경보 → Notifications → Slack Webhook으로 전달한다. 5분 구간의 ERROR 이상을 평가하며 전송 대기 5분·평가 간격 1분, 상태 변경 시 알림이다. 종류별 중복 제거와 앱 정상 판정은 제공하지 않는다. GitHub Actions는 비용을 6시간마다 확인하고 09:13 한국 시각에 일 요약을 보낸다. 실제 연결·검증 상태는 운영 현황을 따른다.

수집·정제 실패는 별도 처리 상태로 남겨 재시도하며 사용자의 대화로 주입하지 않는다. 수집·AI 정제 화면에서 최근 업로드 상태·압축 크기·신규/중복 수·기기별 검증 위치와 정제 실패·재시도·실행 이력을 확인한다. 토큰·원문·지식 본문·프롬프트는 운영 로그에 남기지 않는다. 전체 중단·CPU·디스크·HTTP 경보는 후속이다.

## 첫 배포 다음 작업

[Collector 설치와 정제 설정](agent-memory.md#연결과-지침)을 연결하고 실제 질문으로 지식 품질을 다듬는다. 초기 정제는 청크당 최대 3개 지식 후보와 관련 지식 최대 5개를 비교한다. 이벤트 경계를 우선해 묶고 큰 이벤트는 줄 경계로 나눈다. 성공 청크는 순차 반영·보존하며 전체 청크 완료와 세션 간 통합 품질을 구분한다. 대규모 다중 세션 군집화·자동 목차 생성은 후속이다. 원격 프로젝트 역사는 별도 로컬 파일로 중복 관리하지 않는다.

## 첫 실증의 성공 기준

사용자가 평소처럼 작업하는 동안 대화 삽입·수집 대기 없이 원문이 원격에 쌓이고, 별도 정제 이후 다음 질문에서 근거가 있는 지식을 찾는다. 파일 변경·전송 재시도·정제 실패·지식 개정 충돌에도 원문과 과거 실행을 덮어쓰지 않는다. 어떤 자료가 아직 수집·정제되지 않았는지 구분한다.
