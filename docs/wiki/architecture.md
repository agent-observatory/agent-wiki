# Agent Wiki 아키텍처

**개인 에이전트가 정제하고, 원격 Wiki가 근거와 지식을 보관한다.** 에이전트의 세션이 바뀌어도 현재 결정·제약·남은 일을 다시 찾는 것이 주 용례다. 웹은 읽기·정정·출처 확인을 돕는다.

이 구조를 코드로 구현하고 로컬 검증했다. OCI 운영 전환은 진행 중이다. [실제 운영 상태](../OPERATIONS.md) · [구현 순서와 검증 계획](agent-memory.md) · [이전 서버 정제 구성](../archive/server-ingest/ARCHIVE.md).

## 책임과 비용 경계

| 위치 | 맡는 일 |
| --- | --- |
| 개인 에이전트 | 선택한 대화·코드·문서를 읽고 기존 지식과 비교, 추출·해석·정정·답변 |
| Skill·프로젝트 지침 | 언제 조회하고 정제할지, 어떤 근거와 상태를 남길지 안내 |
| 얇은 CLI | 인증·Workspace 선택·파일 전송·조회·멱등 반영. 자체 모델 호출 없음 |
| Wiki API | 권한·형식·근거 구간·개정 충돌 검사, 원문 등록·지식 반영·검색 |
| PostgreSQL / Object Storage | 지식·개정·리니지 / 비공개 원문 보관본 |

정제는 사용 중인 에이전트의 모델과 사용량을 쓴다. 플랜·API 키 중 어느 방식으로 이용하든 그 에이전트 설정을 따르며, Wiki가 별도 추론 요금을 집계하거나 모델을 호출하지 않는다. 서버 추론 Worker·NVIDIA 호출·pg-boss 큐를 제거했다. GitHub 인증·OCI 저장소·Slack 운영 연동은 유지한다.

## L1–L5와 지식 모델

![개인 에이전트 정제와 Wiki의 지식 계층](../assets/wiki-layers.svg)

L1–L5는 우리 제품의 논리 모델이며 공식 표준이나 서버 안의 직렬 파이프라인이 아니다. L2의 의미 해석과 L5의 답변은 개인 에이전트에서 실행한다.

| 계층 | 역할 | 실행 주체 |
| --- | --- | --- |
| L1 Raw sources | 선택한 대화 발췌·문서·코드의 고정 보관본 | CLI 등록 → Wiki 보관 |
| L2 Ingest | 원문·기존 지식 비교, 주장과 근거 연결, 변경 묶음 작성 | 개인 에이전트 정제 → API 구조 검증 |
| L3 Wiki | Memory·Article·Glossary의 개정과 관계 관리 | Wiki |
| L4 Query | 키워드 조회·시작 Context·인용 자료 구성 | Wiki |
| L5 Answers | 근거를 읽고 현재 질문에 답하거나 작업 | 개인 에이전트 |

Memory는 짧은 주장·결정, Article은 설명 문서, Glossary는 용어·별칭이다. 세 유형 모두 개정 가능한 지식이며 Memory를 거쳐야 Article이 되는 단계는 아니다. Data Lineage는 원문 개정 → 정제 실행 → 지식 개정의 파생 관계다. 관련 문서 링크와 근거 관계를 구분한다.

Schema는 구조·작성 규칙, Index는 목차·검색 색인, Log는 실행 이력, Lint는 누락·상충·오래된 지식 점검을 뜻한다. 서버 Lint는 구조 검사까지, 의미상 상충 판단은 에이전트가 맡는다. LLM Wiki·OpenMetadata의 용례를 참고하되 제품 전체를 설치하거나 우리 확장을 표준으로 부르지 않는다.

## Workspace와 사용자 흐름

Workspace는 자료·권한·검색·Context의 격리 단위다. Folder는 기본 위치 하나, Tag는 다중 분류다. 별도 Label·Project 도메인은 추가하지 않는다. CLI의 프로젝트 이름은 `서버 + Workspace + 프로젝트 태그`를 묶은 로컬 별칭이다.

첫 적용은 `개인 작업` / `개발 기록` / `agent-observatory`, `agent-wiki`다. 다른 Workspace의 근거·지식 연결은 거부한다. 프로젝트 태그는 권한 경계가 아니다.

1. **시작:** 검색어 없이 프로젝트의 현재 결정·제약·미완료 작업·주제 목차를 짧게 조회한다.
2. **작업:** 필요한 주제를 검색하고 근거 구간·과거 개정을 추가로 읽는다.
3. **축적:** 의미 있는 결정·검증이 끝나면 원문 등록 → 정제 → 지식 반영을 수행한다.
4. **재개:** 새 세션은 같은 시작 Context를 조회하고 변경된 결정부터 확인한다.

웹에서는 원문·해당 근거 구간·지식 개정·대체 관계를 확인한다. 작성 주체와 사용자 확인 여부를 분리하며 웹 편집도 같은 개정·근거 규칙을 적용한다. 원문 없는 메모는 작성자 진술로 저장할 수 있지만 자동으로 검증된 사실이 되지 않는다.

## 검색과 Context

초기는 PostgreSQL의 제목·본문·태그·용어 별칭과 명시적 문서 연결을 사용한다. 현재 코드는 키워드와 `pg_trgm` 인덱스를 사용하며 벡터 검색은 없다. 임베딩은 후속 후보이고, 필요할 때 외부 API 또는 사용자가 제시한 Comsat 모델을 별도로 평가한다.

조회 계약은 다음과 같다. 아래는 합성 예시다.

| 입력 | 서버 처리 | 반환 |
| --- | --- | --- |
| 프로젝트 재개 | 프로젝트 시작 문서 + 현재 상태 + 최근 변경 | 결정·제약·미완료 일·주제 목차·근거 개정 |
| `결제 idempotency` | 용어 별칭 `멱등성`, 제목·태그 우선 검색 | 질문 주변 발췌 + 문서 ID·개정·원문 참조 |
| 근거 상세 요청 | 권한 확인 후 고정 개정·구간 조회 | 당시 보관본과 해당 구간 |

시작 묶음은 에이전트가 유지하는 일반 Article을 프로젝트 설정에서 가리킨다. 서버가 요약을 생성하지 않는다. 본문 발췌는 최대 8,000자, 근거·목차를 포함한 전체 JSON은 최대 16,000자에서 시작하고 명시적 문서·구간 조회로 확장한다. Context는 잘림·누락을 표시하고 인용 URL은 고정 개정을 연다. 삭제·대체·미확인 상태를 구분한다.

Context는 최대 6개 지식의 질문 주변 발췌·시작 문서·고정 개정 URL을 반환한다. 근거는 문서당 최대 8개 주장·주장당 4개 출처를 요약하며 잘림을 표시한다. 전체 근거는 지식 개정 API에서 추가 조회한다. 대체된 문서는 기본 검색에서 제외한다. 한국어 띄어쓰기와 별칭 품질은 실제 사용 질문으로 계속 확인한다.

Obsidian의 데이터 관례, 그래프 저장, 웹 시각화는 별개다. 사용자는 Obsidian 앱을 쓰지 않는다. 관계는 PostgreSQL로 시작하며 Cytoscape.js는 후속 시각화 후보다. Apache AGE·OpenMetadata 전체 도입·MCP 서버·로컬 전체 복제는 초기 전환에 넣지 않는다.

## 단일 Compute VM 배포

![개인 에이전트와 4개 컨테이너 목표 구성](../assets/wiki-deployment.svg)

기존 A1 VM 1대·2 OCPU·12GB를 유지한다. 새 Compose는 Caddy·Next.js·Fastify API·PostgreSQL **4개**다. CPU를 공유하고 별도 정제 서버를 두지 않는다.

| 항목 | 목표 구성 |
| --- | --- |
| 메모리 | 기존 Caddy 0.25GB·Web 2GB·API 2GB·DB 3GB 상한 유지. Worker 제거분은 호스트 여유로 둠 |
| 디스크 | 부트 50GB + 연결 Block Volume 50GB. DB·Caddy `/data`·`/config`는 별도 경로 |
| 원문 | 비공개 Object Storage, 마스킹한 보관본·해시·구간. 인증서 저장과 분리 |
| 외부 접속 | `agent-wiki.duckdns.org` → VM Caddy HTTPS. 웹·API는 같은 도메인 |
| 인증서 | Caddy 자동 발급·갱신, 연결 볼륨에 상태 유지 |
| DB 관리 | DataGrip → 공인 5432, 별도 ID/비밀번호·TLS. 사용자 선택에 따라 IP 제한·Bastion 없음 |
| 내부 주소 | `web:3000`, `api:3001`, `postgres:5432`. localhost 공유 아님 |

계정은 사용자가 PAYG로 업그레이드했지만 **유료 사용은 허용하지 않았다.** 이번 앱 전환에서 자원을 추가하거나 사양을 바꾸지 않는다. 실행 시 최신 공식 조건·계정 전체 사용량·Terraform plan을 다시 확인한다. 예산 알림은 강제 지출 상한이 아니다. 백업·복원은 후속 과제다.

## 배포·운영

![4개 컨테이너 배포와 기존 모니터링 유지](../assets/wiki-operations.svg)

Terraform은 인프라, cloud-init은 최초 Docker·마운트 구성, systemd는 부팅, Compose는 실행을 관리한다. OS·Docker·PostgreSQL 업데이트는 직접 맡는다.

배포는 외부 ARM64 빌드·GHCR 게시 → VM 미리 pull → Caddy 외부 신규 유입 차단 → Web의 내부 호출 완료 → API SIGTERM·DB 연결 정리 → DB 변경·변경 앱 교체 → 상태 확인·외부 재개 순서다. DB·Caddy·볼륨을 내리거나 `compose down`하지 않는다. 짧은 중단은 허용한다.

API 종료 예산 30초·Compose 유예 45초를 유지한다. 내부 조회는 deadline 안에서 일시 오류만 backoff+jitter·최대 2회 추가 시도한다. 쓰기는 같은 멱등 키·payload로 결과를 확인하고, COMMIT 응답 유실을 새 쓰기로 처리하지 않는다. 원문 객체 업로드와 DB 트랜잭션은 별개다.

앱은 OTel Logs Data Model에 매핑되는 JSON만 stdout/stderr에 남긴다. Docker syslog → rsyslog → OCI Unified Monitoring Agent → OCI Logging으로 수집한다. 오류 알림은 Connector Hub의 ERROR 이상 필터 → OCI Monitoring 경보 → Notifications → Slack Incoming Webhook으로 전달한다. GitHub Actions는 비용·사용량 알림만 담당한다. 앱에서 직접 Slack으로 보내지 않는다.

| 알림 | 현재 운영 경로 유지 |
| --- | --- |
| 앱 오류 | ERROR 이상 로그가 있는 5분 구간 감지 → 상태 변경 시 알림, 정기 반복 없음 |
| 비용·사용량 이상 | 6시간마다 확인 |
| 데일리 | 09:13 한국 시각, 비용·사용량·전일 비교 가능한 항목 |

새 전환에서는 정제 실패를 개인 에이전트와 CLI에 표시한다. 서버 반영 실패는 API 오류 로그로 남긴다. 지식 본문·원문·프롬프트·토큰은 운영 로그에 남기지 않는다. 경보 평가는 1분 간격이며 로그 전송을 위해 5분의 집계 대기를 둔다. 오류 종류별 중복 제거는 하지 않는다. 경보 해제는 앱 정상이나 로그 수집 정상의 증명이 아니다. 전체 중단·CPU·디스크 경보는 후속 과제다.

GitHub 소유자 로그인과 Workspace별 API 키를 유지한다. 새 권한 계약으로 키를 다시 발급하고 기존 키·수집 API는 폐기한다. 로컬 비밀은 Git 제외 `.env.local`에 둔다.

## 첫 배포 다음 작업

[실행 계획](agent-memory.md#전환-순서)의 순서대로 새 원문·리니지·반영 계약 → CLI·Skill → 시작 Context·웹 근거 → 역사 재작성 준비 → 데이터 초기화·Worker 제거·일괄 교체 → 실제 사용 검증을 진행한다. 로컬 검증을 완료했으며 운영 전환과 실제 에이전트 조회를 확인한다.

하위 호환성은 요구하지 않는다. 앱·데이터 계약을 새로 만들고 기존 Wiki 데이터·API·키를 교체한다. VM·인증서·OAuth·모니터링은 재사용한다.

## 첫 실증의 성공 기준

새 세션에서 프로젝트 연결만으로 “Atlas에서 왜 독립 Wiki가 됐고, 지금 어떤 결정과 미완료 일이 남았나?”를 찾아 답한다. 인용을 열면 실제 보관본의 정확한 구간이 보이며, 다른 세션에서 정정한 결정이 재조회에 반영되어야 한다.

반영 재시도·개정 충돌·Workspace 격리·근거 누락·삭제·서버 단절도 확인한다. 저장하지 못한 대화 복구나 모든 에이전트의 자동 컴팩션 감지는 완료 기준으로 약속하지 않는다.

무신사 글의 2층 구조는 산업 표준을 정리할 수 있는 도메인을 전제하며 큐레이션 비용이 든다. 150개 질문에서 레이어 유무를 비교했지만 같은 지식을 담은 평면 문서와 직접 비교하지는 않았다. 우리 Wiki에 Core·Overlay를 새 계층으로 도입하거나 그 구조의 효과가 검증됐다고 해석하지 않는다.

원본 링크와 사용자 메모는 [레퍼런스 목록](README.md#레퍼런스)에 보존한다. NAVER의 OpenMetadata 활용은 사용자 제공 메모이며, 위 표는 공식 발표 소개에서 확인한 범위다. GeekNews 글은 Karpathy 원문을 소개하는 자료로 함께 참고한다.
