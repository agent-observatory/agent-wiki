# Qwen thinking 소규모 비교

**임시 선택: 추론 끔.** 개인 위키의 초기 가설이며 Qwen 전체 성능이나 실세션 정제 품질의 결론이 아니다.

2026-09-13, Singapore `qwen3.7-flash-2026-07-15`. 기존 합성 판단 사례 6개를 3개씩 두 입력에 묶어 off/1024/2048을 각 2회 호출했다. 전체 **6 HTTP 요청·12,031 토큰**, 입력 본문 포함 요청은 약 2.4–2.6KB. 재시도·실제 세션 전송·Wiki 쓰기는 하지 않았다. `max_completion_tokens=4096`, 모델의 나머지 샘플링 기본값을 사용했다. 동일 입력·프롬프트로 비교하고 두 번째 묶음은 호출 순서를 뒤집었다.

| 설정 | 분류 일치 | 모든 계약 일치 | 입력 | 출력 (추론 포함) | 추론 부분 | 합계 응답 시간 |
| --- | --- | --- | --- | --- | --- | --- |
| off | 5/6 | 2/6 | 1,089 | 896 | 제공자 미제공·추론 비활성 | 10.1초 |
| thinking_budget=1024 | 4/6 | 2/6 | 1,085 | 2,890 | 2,048 | 31.6초 |
| thinking_budget=2048 | 3/6 | 1/6 | 1,085 | 4,986 | 4,096 | 46.8초 |

‘모든 계약’은 분류·대상·검증 여부·원문 인용을 모두 만족한 사례다. 세 조건 모두 검증되지 않은 내용을 `verified=true`로 승격하지 않았다. 늦은 과거 발언을 덮어쓰지 않은 응답도 기대한 `historical` 대신 `unconfirmed`를 반환하면 분류 불일치로 센다. 따라서 점수만으로 의미 판단 전체가 틀렸다고 해석하지 않는다.

공통 문제는 `prior.source.text` 원문 대신 `prior.text` 요약을 인용한 것이다. 2048에서는 검토 의견·확인되지 않은 완료 보고의 분류도 기대와 달랐다. 추론 예산을 늘리기만 해서 해결되지 않았으며, 현재 소표본에서는 늘릴 근거가 없다. 이는 실제 Worker의 전체 발행 스키마를 실행한 검사가 아닌, 기존 판단용 프롬프트를 사용한 독립 비교다.

실제 운영에서 인용·관계 오류가 생기면 해당 입력·당시 설정·응답·검증 이유로 작은 재현 사례를 만든다. 원문과 참고 요약의 표현을 먼저 점검하고 필요할 때만 추론 예산이나 프롬프트를 비교한다. 정기 대규모 평가·자동 다중 모델 호출은 하지 않는다.

- [입력 사례](../cases.json) · [스크립트](compare.mjs) · [결과](results.json)
- 출력은 합성 자료이며 reasoning_content·키·비공개 주소를 기록하지 않는다.
- 스크립트는 수동 실행 전용이다. 다시 실행하면 무료 쿼타를 추가 소비한다.
- [공식 파라미터](https://www.alibabacloud.com/help/en/model-studio/qwen-api-via-openai-chat-completions): Qwen 3.7은 enable_thinking/thinking_budget으로 비교하며 reasoning_effort 등급을 임의로 매핑하지 않는다.
